> 本文是针对指定 APK 的本地研究记录，不提供修改版 APK、签名私钥或可直接套用的补丁脚本。请只在有权测试的环境中研究，并自行确认软件协议与使用风险。文中的实机结果仅覆盖这次实际观察到的路径，**不代表全部广告、全部功能或其他版本已经验证**。

这次最值得复盘的，不是“找到了两个广告方法”，而是前后两次判断修正。

第一次，看到网易加固、JADX 只能解析出壳类，过早地认为必须连接设备才能继续。实际上，同一工作区此前分析虎扑时留下的离线恢复脚本，就能用于验证酷安的容器格式。

第二次，广告补丁、签名和文件校验全部通过，手机也能进入首页，却加载不出数据。真正遗漏的是**业务层自己的证书校验**：加固层接受新签名，不等于请求令牌生成逻辑也接受它。

下面按证据出现的顺序，记录这两次修正。

## 1. 样本很大，能看到的却只有 31 个类

分析输入是酷安 `16.6.4`，包名 `com.coolapk.market`，versionCode `2609291`，minSdk 24、targetSdk 34。原 APK 的 SHA-256 为：

```text
9a2be68a5dbb500f40fdd5e183ef36388dec676caaaa23a5a872429ddbba9eff
```

REA 的 Android 包检查和完整类名查询显示，JADX 只能解析到 **31 个类**，主要位于 `com.netease.nis.wrapper`。唯一的 `classes.dex` 却有 **102,655,212 字节**。

壳的启动链也很明确：`MyApplication.attachBaseContext()` 加载 native 库并调用 `MyJni.load()`，之后创建真实 Application；`onCreate()` 再经 JNI 调用转入真实应用。这只能说明眼前分析的是壳，不能据此认为业务代码不存在。

包内还能找到穿山甲、广点通、快手和 AnyThink 的文件、广告位配置及相关 native 库。但这些只是**组件存在的证据**，既不能证明 SDK 在当前页面执行，也不能直接给出安全的广告切点。删除整个 SDK 或 Manifest 组件，反而可能制造类加载错误。

当时的初步判断是需要运行时还原。用户提醒：此前虎扑也是网易加固，而且已经在同一目录完成了离线恢复。这个提醒把下一步从“先找设备”变成了“先检查已有研究能复用哪一层”。

## 2. 能复用的是容器算法，不是上一款应用的补丁

[虎扑案例](/posts/hupu-protected-dex-ad-patch-case-study/)已经定位过一种封装：业务 DEX 放在壳 DEX 标准 data 区之后的附加容器中。复用时，没有把旧脚本直接当作通用解密器，而是逐项核对酷安的实际字节：

| 检查项       | 酷安样本中的结果                    |
| ------------ | ----------------------------------- |
| 容器起点     | `data_off + data_size = 0xf960`     |
| 容器包名 CRC | 与 `com.coolapk.market` 匹配        |
| 配置解码     | 得到正确包名及真实 Application 名称 |
| 记录数量     | 10 条业务载荷记录                   |
| 记录类型     | 均为当前恢复器支持的 type=5         |
| 长度关系     | 存储长度与明文长度均相同            |
| 输出完整性   | 10/10 原始 SHA-1、Adler32 匹配      |

配置解码方式与虎扑兼容，但业务 DEX 使用的是**酷安自身配置中的密钥**，不能套用虎扑的值。每条记录独立初始化 RC4，只处理前 `min(载荷长度, 4096)` 字节，剩余部分原样保留。本样本未命中解压分支，因此不能把那个分支写成实测通过。

最终恢复出 **10 个业务 DEX，共 100,645 个 class_def**，头字段、固定节区和 map 范围检查通过。没有通过重写头部或重算原始校验值来“修到能过”。

这里要区分三种复用：

- **恢复算法可以验证后复用**：格式、包身份、边界和原始校验都能交叉核对。
- **广告补丁不能照搬**：虎扑的类、方法和偏移不属于酷安。
- **保护策略不能照搬**：即便同属一个加固产品，配置位与执行路径也需要当前样本的证据。

原 APK、虎扑恢复脚本和旧补丁产物没有修改；酷安的恢复、构建和验证都放在独立目录。

## 3. REA 负责定点取证，不必强求一次分析完整应用

恢复后的全部 DEX 组成分析 ZIP 后，首次 REA 类搜索遇到了客户端 60 秒超时。这个结果不能被解释为“恢复失败”，也不能冒充完整反编译已经成功。

随后先直接解析 DEX 的 `class_def`，建立类到 DEX 的索引，再把主要广告代码所在的 DEX7、DEX8 分别交给 REA。较小范围的类检查、方法反编译和入引用查询成功返回，结合本机 JADX、Baksmali 与原始指令交叉核实。

主要定位到两组候选：

```text
DEX7：EntityAdHelper、EntityDelayLoadADHelper、ScopeAdManager
DEX8：SplashAdLoader、SplashAdFragment、SplashAdActivity
```

这些名称只是分析入口。是否能修改，仍要看**方法做什么，以及调用方如何处理它的返回值**。另外，REA/JADX 展示的 `mNNNN` 是引擎生成的别名；实际补丁按原始 DEX 方法名和精确签名匹配，不能跨工具直接套展示名。

恢复完整 DEX 文件也不意味着所有方法语义都已恢复。后续就发现部分插屏入口是 native 方法；对这些路径，本轮没有凭猜测修改。

## 4. 信息流：复用已有过滤分支，而不是全局改隐私状态

`EntityAdHelper` 中有一个处理实体列表的方法。原逻辑先处理刷新时的旧广告资源，再查询隐私同意状态：

```text
输入实体列表
  → 必要的刷新清理
  → 查询隐私状态
      ├─ 未同意：按已有模板数组过滤 sponsor 卡片，返回新列表
      └─ 已同意：继续广告卡识别、缓存处理及预加载设置
```

模板数组包含五类：

```text
sponsorCard
sponsorFeed
sponsorArticleNews
feedDetailReplySponsorCard
sponsorForSearch
```

这个现成分支提供了比“广告 View 设为 GONE”更合适的切点：广告实体在进入后续列表流程前就被排除，而不是保留数据条目、只隐藏控件。

补丁只在 **EntityAdHelper 这一处调用位置**，将查询结果替换为 `false`，使方法走已有的 sponsor 模板过滤分支。并没有修改全局隐私工具、用户协议状态或用户设置，也没有按营销文字、通用帖子类型粗删内容。

替换保持 8 字节等长，保留原来的分支偏移和寄存器布局。静态语义上，未命中模板的正常实体保持相对顺序；但这不等于已经实测所有列表、分页和缓存路径都安全。

## 5. 开屏：返回 null 之前，先找清楚谁负责收尾

开屏的核心路径是：

```text
MainActivity / SplashAdActivity
  → SplashAdLoader 默认参数桥接
  → 加载入口
  → SDK 初始化与广告加载协程
  → 成功或失败回调
  → 展示或结束
```

简单让某个回调不执行，可能留下倒计时、透明遮罩或返回键拦截。因此这里没有先改 Fragment 的展示方法，而是检查加载入口返回“无广告源”时，两个已知宿主会怎样处理。

静态调用链给出了明确的收尾分支：

- **MainActivity**：隐藏开屏层，调用原会话结束方法，恢复相关交互状态，执行关闭回调。
- **SplashAdActivity**：调用原结束方法，设置结果、结束 Activity 并执行原有退出过渡。

据此，在 `SplashAdLoader` 的加载入口返回 `null`，不启动后面的 SDK 初始化与加载协程，让宿主继续使用自己的无广告源分支。入口仅用 4 字节等长替换，没有重写 Fragment 生命周期或整个 DEX。

这不是“所有广告 SDK 都不再初始化”的证明：构造器、其他独立初始化入口、反射和动态加载仍有边界。它只是针对已核实的两条宿主调用链，选择了有依据的退出方式。

两处广告补丁最终只修改了 **2 个业务 DEX、2 个方法**。其余 8 个业务 DEX 保持原样。

## 6. 回装时保留检查，比照搬关闭开关更容易复核

回装仍使用原来的附加容器格式：载荷等长、记录表不变、偏移不变、间隙和尾部保留。修改后更新业务 DEX 及外壳 DEX 的必要校验字段，再使用独立测试证书签名。

重签名还带来两项适配：

1. 加固配置中的预期证书摘要，改为测试证书的真实摘要，其他配置键和策略位保持不变。
2. 更新文件完整性清单中发生变化的成员 CRC。

第二项没有直接沿用虎扑的策略调整。对酷安的 `assets/nedig.properties` 做字节分析后，恢复出一个周期 XOR 编码的文件清单。解码结果中的 **61 条文件 CRC 全部与原 ZIP 成员匹配**，为格式推导提供了很强的交叉验证。

因此首版只更新清单中 `classes.dex` 的预期 CRC，再按原方式编码，没有盲目关闭相似的保护开关。文件级校验包括：

- 签名后重新恢复容器，10 个业务 DEX 均与预期完全一致。
- 两个修改 DEX 中，其他有代码的方法指令逐一保持一致。
- ZIP CRC、61 条清单记录、APK 签名及 zipalign 通过。
- 完整重建后，最终签名 APK 与首份逐字节一致。

**这些都通过了，手机仍然可能不能正常使用。** 接下来的 403 正好说明了这一点。

## 7. 能进入首页，却加载不出数据

首版安装后，应用能进入 MainActivity，但列表显示加载失败。用户连接设备后，先核对设备端 `base.apk` 的 SHA-256，确认安装的确实是交付的首版，而不是另一个历史文件。

点击失败页面重试，日志出现列表接口的 **HTTP 403 Forbidden**。这首先纠正了一个可能的误判：不是 sponsor 过滤把正常列表“删空”，而是请求没有成功得到数据。手机当时开启了 VPN，用户关闭后仍然复现，随后继续沿请求构建路径排查，而不是反复切换网络。

更关键的日志在 403 之前：

```text
java.lang.RuntimeException: Application signature verification failed
    at com.coolapk.market.util.AuthUtils.getToken(Native Method)
    at …AppConfig…
    at …CoolMarketHeaderInterceptor.intercept(…)

GET …/v6/page/dataList → HTTP 403 Forbidden
```

只看到 403，不能直接认定是哪项校验失败；这段前置异常和调用栈，才把调查范围缩到了请求令牌生成。

REA 切换到 `libauth.so`，由 Ghidra 分析具体函数后发现：

- `AuthUtils.getToken()` 在生成令牌前，先调用独立的应用签名校验。
- 校验经 PackageManager 读取应用签名，转换成证书十六进制字符串。
- 库中固定了一份官方证书，检查长度后对完整字符串执行比较。
- 校验失败会抛出与日志一致的异常，不进入正常令牌生成逻辑。

这份证书常量解码后的摘要与原 APK 签名匹配。首版修改的只是**加固容器中的证书预期值**，没有适配**业务认证库中的另一份固定值**。两者不是同一个开关。

因此本轮能建立的故障链是：

```text
重签名
  → libauth 独立证书校验不接受新证书
  → 请求令牌生成报错
  → 同次列表请求随后返回 403
```

后续修复及实机恢复又补上了这条因果链的验证，而不只是停留在静态猜测。

## 8. r2 保留完整证书比较，不修改令牌算法

修复没有把校验函数改成无条件成功，也没有伪造 Android 系统报告的官方签名，而是让这个本地测试构建的预期证书，与它自己的测试签名一致。

这里还有一个实际的 ELF 布局问题：原证书字符串长 **1,210 个字符**，测试证书字符串长 **1,702 个字符**。不能简单把长字符串覆盖进去，否则会破坏相邻数据；也不能看到某片区域全是零，就认为它能安全使用——那里可能是等待重定位的数据或运行时需要的结构。

本样本的处理是为完整测试证书增加一个只读加载区域，利用原 `PT_NOTE` 的程序头槽描述新的 `PT_LOAD`。原 note sections 仍保留在文件中，新区域不与原加载区、BSS 或 RELRO 重叠。这是**针对当前 ELF 的布局选择**，不是任意 Android 库都能直接套用的通用做法。

校验函数中只调整证书地址、分配长度、复制长度、终止位置和长度比较等操作数；原调用、条件分支和完整字节比较仍然保留。REA 重新导入修改后的 ELF，反编译结果确认它比较的是完整的 1,702 字符证书。

同时，更新文件清单中 `libauth.so` 的 CRC，并保持：

- 同一测试签名，方便覆盖当前测试版而不卸载。
- 首版两个广告补丁及全部 DEX 字节不变。
- 请求令牌算法不变。
- 加固策略位不变。
- 其他非目标 ZIP 成员内容不变。

这时仍只能说静态修复具有依据，不能跳过安装验证。新增 ELF 段能否被设备正确加载，本身也是必须验收的项目。

## 9. 真机结果，以及没有验证的部分

获得用户明确许可后，使用同签名覆盖安装，没有卸载或清数据。设备端 APK 哈希与本地 r2 一致。显式停止进程后重新启动，系统记录为 **COLD**，MainActivity 保持前台。

实际截图显示，此前失败的“话题／热门”页面加载出了图标、话题和热度数据。用户随后反馈：**“可以了。”** 本次新进程的有界日志中，也没有再出现之前的签名校验异常、HTTP 403 或致命异常。

这证明本轮修复恢复了已复现页面的数据加载，且新 ELF 布局在该设备上实际加载成功。它不证明所有接口、所有设备或未来的日志窗口都不会出错。

| 验证对象           | 本轮能够支持的结论                                 |
| ------------------ | -------------------------------------------------- |
| 离线恢复           | 10 个业务 DEX 的原始校验匹配；不等于完整 ART 验证  |
| 广告补丁           | 两个方法有可追踪的过滤／收尾依据，其他方法差异受控 |
| 构建与签名         | 文件、清单、签名、对齐和重建一致性检查通过         |
| 首版故障           | 同次重试观察到业务签名异常及后续 403               |
| r2 运行            | 覆盖安装、冷启动、原失败页的数据加载已验证         |
| 全部广告及账号功能 | 未完整验证，不能宣称通过                           |

部分 native 插屏、激励视频、商城及 WebView 广告路径未证明覆盖；长后台热启动、多轮刷新和分页、登录及第三方授权也没有完整验收。信息流过滤虽有明确的静态依据，**这次数据恢复的截图不是“全部信息流广告均已清除”的证据**。

## 10. 这次真正值得复用的是什么

如果把过程压缩成几条经验，我会保留下面这些：

1. **别把工具当前可见范围，当作目标全部内容。** 31 个壳类和一个很大的 DEX，是继续研究封装的线索，不是业务代码不存在的结论。
2. **先复核已有成果，再要求更重的运行环境。** 虎扑的离线恢复链解决了这次最早的阻塞，但类名、补丁和策略不能随之照搬。
3. **补丁安全性来自调用方契约。** 信息流复用现有过滤分支；开屏先核实无广告源时谁负责恢复状态，而不是只让加载函数空返回。
4. **加固接受、业务认证接受、服务端接受是不同层次。** 首版正是只处理了其中一层。
5. **“验证通过”必须带宾语。** ZIP 校验通过、签名通过、能启动、能加载数据、广告效果通过，是不同命题。
6. **用故障前的日志修正猜测。** 403 本身信息有限；令牌生成前的签名异常，才是这次修复的关键。

最终结果不是一个没有边界的“去广告成功”，而是：完成了两处有证据的本地广告补丁，修复了一项由重签名引入的业务认证兼容问题，并在授权设备上验证了冷启动和原失败页面的数据恢复。
