> 本文记录对指定版本 APK 的研究过程，不是通用去广告教程或官方客户端的发布说明。分析和测试应限于自己有权操作的设备与软件。文中**不提供修改版安装包**；不同版本的类名、偏移和行为可能完全不同。

## 从一个容易误判的问题开始

目标样本是 X Android `com.twitter.android`，版本 `12.34.0-prod.01`（versionCode `312340001`），输入为多分包的 `x.apkm`。初始目标是研究时间线里的推广内容如何进入列表，而不是仅仅隐藏一个带“广告”字样的 View。

第一步先确认样本身份和边界：从 APKM 提取主包，用 `aapt2` 核对包名、版本与 SDK；对 DEX 做定点检索和 JADX 反编译，而不是假设反编译出来的 Java 一定能直接重新编译。原始 APKM 的 SHA-256 为 `b7bd98c97fcf6fdfcafc39e10f3c37e66d9f98c78de4470dea9c69688c955a10`。此次重点是主包 DEX；native、动态模块、账号实验组和实时服务端响应不在完整审计范围内。

## 沿着数据，而不是沿着“广告”两个字找

在该版本的模型字段中，`promoted_metadata` 与 `preroll_metadata` 同时存在，但意义不同：前者可用于识别被推广的时间线条目，后者涉及视频前贴片，不能混为一谈。推送到屏幕前，条目还经历了一系列转换：

```text
GraphQL 时间线指令（AddEntries / ReplaceEntry / AddToModule 等）
  → 时间线仓库解析指令
  → entry / module 映射器
  → 帖子、用户或独立 RTB 广告模型
  → presenter / 列表渲染
```

定点反编译显示：仓库中的 `com.x.repositories.urt.h1` 处理新增、替换、置顶和模块更新；`coil3.network.g.K` 组织 entry/module，`coil3.network.g.J` 将单个条目转换为模型。这里的 `coil3.network.g` 是**混淆和优化后落在该包中的位置**，不能理解为原始 Coil 库在投放广告，更不能跨版本复用这个名字。

关键发现不只是“某个字段非空”，而是**调用者能容忍单条映射结果为 `null`**：顶层只加入非空条目；模块子项先过滤，再计算剩余数量和位置；另一条模块包装路径同样会跳过空结果。这样，比在列表渲染后把 View 设为 `GONE` 更合理的切点，是在模型进入列表之前决定是否保留它。

概念上，这个切点相当于：

```text
映射一个条目
  ├─ 独立 RTB 图片广告模型？丢弃
  ├─ 帖子/用户模型携带推广元数据？丢弃
  └─ 其他模型（包括游标、普通帖子）？保留
```

这仍是由静态控制流推导的方案；`null` 路径存在，不代表真实环境下分页、去重、缓存和模块更新的所有不变量都已验证。尤其不能根据关键词或通用 `viewType` 删除帖子：普通内容也可能包含商业词汇、视频信息或卡片。

## 还有一条独立广告路径

该样本另有 SSP 广告模式选择路径，包含 `ClientDriven`、`ServerSlotClientFetch`、`ServerToServer` 等模式，并受 `android_x_lite_ssp_ads_enabled` 等开关影响。只屏蔽 SSP 并不会移除已经由时间线服务端作为推广条目下发的内容；反过来，只过滤推广元数据，也不能自动覆盖独立 RTB 或其他广告通道。因此分析把**条目级过滤**与**广告专属 SSP 门控**作为两项互补措施，未修改订阅、Premium、登录或付费权限状态。

研究过程中先写过一个限定包名和版本的 Frida 概念验证脚本 `analysis/x-feed-noads.frida.js`，用 Node mock 测试覆盖普通帖、推广帖、用户推广、RTB、游标、异常放行及版本检查。**mock 测试不是设备测试**；它无法证明真实 Frida Java 桥、类加载器和列表滚动都正常。之后制作了一个重签名的单 APK 本地测试构建：将原多分包合并，给条目转换入口加过滤包装，并调整 6 个 SSP 专属方法。主 DEX 的方法引用已满，所以目标类迁往新增 DEX，而不是简单往原 DEX 塞代码。

静态校验的结果是：补丁 DEX 能重新解析，方法引用未超限；规范化对比中非目标代码/元数据保持不变，另有 5,135 个合并条目解压后内容逐字节保持一致；测试签名通过 APK Signature Scheme v3 校验。**这些都是文件级验证，不等于应用已在无 root 设备上正常运行，更不等于广告已彻底消失。**重签名包也通常不能覆盖官方签名安装。

## 这次实践留下的方法论

1. 从网络字段追到**数据模型及其所有消费者**，而非只查广告 SDK 名字。
2. 同时覆盖帖子化推广、独立广告模型和广告模式选择；避免误删正常帖子与游标。
3. 在边界处保留明确的失败策略：模型分类不确定时放行，而不是让时间线整体崩溃。
4. 把“能静态复核补丁”与“真实设备的效果”分开陈述。缓存条目、视频前贴片、动态模块、未来服务端格式仍是明确的残余范围。

后续若做实机验收，需要分别刷新推荐与关注流、多页翻页、检查模块增删和缓存、观察崩溃/ANR；仅凭一次首页截图不能得出“全部广告已移除”的结论。
