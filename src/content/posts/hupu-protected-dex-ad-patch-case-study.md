> 这是一份针对 `com.hupu.games` 指定样本的研究记录，不提供 APK、签名密钥或规避策略的可直接套用脚本。改包可能违反软件协议；请只在有权测试的环境中研究。文中的“验证通过”都标明范围，**不等于可替代官方版本使用**。

## 为什么直接反编译看不到业务代码

输入是虎扑 `8.2.63.09241`（versionCode `12314`）的 `hupu.apk`，SHA-256：`f0b557459868d39ee1e99c3db5478c7fe78c3c3186ce9777fcbb02fff368051f`。Manifest 声明的 Application 是壳类 `com.netease.nis.wrapper.MyApplication`；它在 `attachBaseContext()` 中调用 native 加载逻辑。尽管主 `classes.dex` 解压后约 100 MB，常规 JADX 只能看到约 32 个静态类：不能据此断言广告代码不存在，也不能靠删除 Manifest 中的广告 Activity 来可靠跳过开屏。

研究的第一个任务因此不是“改广告”，而是回答：**业务 DEX 到底来自哪里，能否只读、离线地恢复？** 初步 native 分析找到壳 DEX 的 data 区结束位置：`data_off + data_size = 0x10314`。这并非整个 DEX 文件的末尾，而是附加封装容器的起点。容器先存包名 CRC、加密配置和记录表，再保存业务载荷。对静态指令、容器布局和实际字节做交叉校验后，确认本样本的 20 条 type=5 记录都落在原始 `classes.dex` 成员中。

简化的数据路径如下：

```text
原 APK 的 classes.dex
  → 标准 data 区之后的附加容器
  → 配置解码、记录表解析
  → 对每条载荷独立解码
  → 20 个业务 DEX
  → 壳在运行时交给 ART 的加载路径
```

配置与业务载荷使用不同的变换环节。恢复出的配置 `d:` 提供业务 DEX 所需的 ASCII 密钥；每条载荷重新初始化 RC4，**只处理前 `min(载荷长度, 4096)` 字节**，后面的字节原样保留。本样本所有记录的存储长度和明文长度相同，未走解压分支；不能把未覆盖的分支写成“已实测”。离线脚本按原容器记录恢复了 **20 个业务 DEX，共 82,259 个 class_def**，20/20 的原始 SHA-1 与 Adler32 匹配，并通过头字段、节区与 map 范围校验。业务入口 `com.hupu.games.HupuApplication` 也在真实 `class_def` 中定位，而不是只在字符串表里找到名字。

这些校验证明文件恢复具有可复核的完整性，**不代表所有方法都具备可执行语义**。例如恢复的 `SplashFragment.showSplashAd()` 等部分方法指令是全 `nop`，静态视角不能完整解释冷启动回调和潜在运行时补全。

## 找到广告真正进入页面的地方

拿到业务 DEX 后，才对 20 个 DEX 一起做定点 JADX、smali 和原始指令的交叉分析。开屏一侧，`HpSplashAd.load()` 管理 listener、超时、请求和失败回调；热启动还会经过 `BootPreLoadManager`、`HpAdBootLifecycle` 与专用广告 Activity。如果粗暴让 `load()` 空返回，可能使调用方永远等不到回调、卡在开屏。因此研究选择保留原有失败状态与 `onError` 路径，并在广告 Activity 路由前阻断热启动展示。

信息流一侧，推荐页和关注页的广告管理器最终汇入 `HpFeedAd`：

```text
推荐/关注页 → 各自的 AdManager → HpFeedAd.loadData
  → 获取页面广告配置 → canLoadAd
  → 缓存消费或请求 → loadSuccess → adapter 插入
```

其中广告不一定长得像单独的广告卡片：`showType=24` 的线程广告还可能被包装成帖子样式。按“帖子类名”或 `viewType` 统一删除会误伤正常内容，也可能留下空白；选择在广告专属的 `canLoadAd` 门控处阻断，避免触及正常帖子分页和 adapter 的通用插入逻辑。

原型补丁一共落在 **2 个业务 DEX、5 处指令**：开屏请求走原失败回调、禁止热启动预加载和缓存命中、在热启动广告路由前返回、关闭信息流广告加载门控。替换保持指令长度和 DEX 布局；再按原封装格式回装等长载荷，重算校验字段。未修改的 18 个业务 DEX 保持原 SHA-256，签名后重新提取的 20 个 DEX 与预期一致。测试包使用独立签名，未冒充官方签名，也没有把分析用的合成 native ELF 装回 APK。

## 一次失败，比“补丁成功”更有价值

第一版文件级验证通过，但安装后出现“请在官方渠道下载正版app”，进程自行退出。此时不能把签名通过说成启动成功，更不能继续盲改广告函数。研究制作了一个**只重签原包、不改业务代码**的控制包；它也以相同模式退出。这将问题从“广告补丁写错了”缩小到“重签名后的启动保护条件”。

后续只读观测和静态回溯发现两个相关检查：证书摘要与预期配置是否一致，以及 APK 文件清单/CRC 是否符合壳的策略。单独适配测试证书、单独尝试配置已有的跳过证书选项，都没有让应用成功启动；运行时读到的配置证明这些改动确实被加载，不能再将证书问题当作唯一解释。进一步定位到文件清单回调会读取 `assets/nedig.properties` 并写入共享拒绝标志。最终测试方案**保留证书匹配逻辑并适配测试证书，仅关闭这一条文件清单/CRC 回调的注册**，没有全局移除退出行为或替换 native 库。

最新的 r2 测试版在手机上安装成功，设备端 APK 哈希与本地一致；首页和内容显示，显式停止进程后重新冷启动仍能进入 MainActivity。这个结果修正了早期“启动失败”的结论，但**还不能声称全部广告已清除**：多轮刷新和分页、关注流、长时间后台热启动、登录及所有 A/B 路径尚未完整验收。之前的 35 秒热启动序列被中止，不能算通过。

## 值得保留的三层证据

| 层次               | 能证明什么                                            | 不能证明什么                             |
| ------------------ | ----------------------------------------------------- | ---------------------------------------- |
| 容器与 DEX 校验    | 20 个文件按原格式恢复；补丁后的校验和及未改文件可复核 | ART 已运行所有方法、运行时补全机制已解释 |
| APK 构建与签名     | ZIP、对齐、签名及回环提取结果符合预期                 | 重签名后的保护或服务端一定接受           |
| 控制实验与设备观测 | 控制包同样退出；r2 在已测冷启动与内容显示路径工作     | 所有页面与广告类型都已覆盖               |

这次案例最重要的不是“五处补丁”本身，而是处理不确定性的方法：先恢复真实输入，再按专属广告管道找切点；用**仅重签对照包**区分补丁问题与保护问题；最后只把已经观察到的运行结果写成结论。测试安装包与原版签名不同，通常不能覆盖官方安装，不建议为了验证而卸载日常使用版本或清除用户数据。
